# 상위노출 조사 (study)

**목적 하나입니다.** 우리가 노리는 키워드에서 상위에 올라가서 **유지되고 있는** 글을
반복해서 재고, 앱이 쓰는 기준(글자수·이미지 수·정보 종류·홍보 종류·어미…)이 아직 맞는지
점검합니다.

이게 필요했던 이유는 실제로 틀렸던 적이 있기 때문입니다. 11편을 세서 잡은 「홍보 표현이
많으면 순위가 내려간다」는 기준이, 141편으로 다시 재보니 **틀렸습니다** (홍보 종류 수는
순위와 관계가 없었고, 갈린 것은 정보 종류 수였습니다). 손으로 한 번 재고 끝냈으면 그 오답이
계속 남았을 겁니다.

## 쓰는 법 — 쌓기는 자동입니다

**배포된 앱이 매일 하나씩 쌓습니다** (`/api/cron/study`, 매일 18:00 UTC). 손으로 돌릴 필요가
없습니다. 분석할 때만 내려받으면 됩니다.

```bash
npm run study:pull -- --url=https://your-app.vercel.app   # 쌓인 런 내려받기
npm run study:analyze                                     # 기준 점검 → study/report.md
```

직접 재고 싶을 때만:

```bash
npm run study:collect     # 지금 순위를 재서 study/runs/<날짜>.json 에 저장
```

`collect` 는 문단 구조까지 잽니다 (크론은 안 잽니다 — 아래 「크론과 로컬의 차이」). `pull` 은
같은 날짜의 로컬 런을 **덮어쓰지 않습니다.**

### 왜 하루씩인가

「유지하고 있는 글」을 가리는 데 필요한 것은 런 **개수**가 아니라 **기간**입니다. 하루씩
쌓으면 이 주면 14개 런이 14일을 덮습니다 — 손으로 주에 한 번 돌리는 것보다 촘촘하고,
올라갔다 사라지는 글이 훨씬 빨리 걸러집니다.

`analyze` 는 첫 런과 마지막 런의 **간격이 3일 미만이면** 「이 유지는 믿지 마세요」를 먼저
띄웁니다. 몇 시간 동안 순위가 안 바뀐 건 유지가 아닙니다.

### 크론과 로컬의 차이

| | 크론 (매일) | 로컬 `collect` |
| --- | --- | --- |
| 순위 | 키워드 전부, 매일 | 키워드 전부 |
| 본문 | **7일 넘게 묵은 것만** (한 번에 최대 60편) | 캐시가 오늘 것이 아니면 전부 |
| 문단 구조 | 안 잽니다 | 잽니다 |

크론이 본문을 나눠 받는 이유는 비용입니다 — 키워드 22개 × 상위 10편이면 매일 본문 160편을
읽어야 하고, 그건 함수 한 번(300초)에 들어가지 않습니다. **순위는 매일 바뀌고 본문은 거의
안 바뀌므로** 순위만 매일 전부 받습니다. 유지 판정은 순위 이력으로 하니 흐려지지 않습니다.

못 받은 본문 편수는 크론 응답의 `bodiesDeferred` 에 적힙니다 — 조용히 줄이지 않습니다.

옵션:

```bash
node scripts/study.mjs collect --keywords="쌍용동 헬스장,천안 PT" --top=10
node scripts/study.mjs collect --cache-days=3   # 3일 안에 받은 본문은 다시 안 받는다
```

**캐시는 하루만 듣습니다.** 같은 날 여러 번 돌릴 때만 재사용하고, 날이 바뀌면 본문을 다시
받습니다. 캐시가 영구적이면 그동안 수정된 글의 옛 수치가 계속 나와서, 순위는 변하는데 내용은
안 변하는 조사가 됩니다. 급할 때만 `--cache-days` 로 늘리세요.

조사 키워드는 `study/keywords.json` 에서 고칩니다. 유지력을 보려면 몇 개는 그대로 두세요 —
키워드를 다 바꾸면 예전 런과 비교할 대상이 없어집니다.

## 나오는 것

| 파일 | 커밋 | 내용 |
| --- | --- | --- |
| `study/runs/<날짜>.json` | O | 그날의 순위 + 측정값 (본문 없음) |
| `study/report.md` | O | 사람이 읽는 리포트 (analyze 출력 그대로) |
| `study/findings.json` | O | 항목별 판정 (`confirmed` / `keep` / `stricter` / `change` / `insufficient`) |
| `study/.cache/` | X | 받아온 원본 HTML (**같은 날**에만 재사용) |

크론이 쌓는 곳은 파일이 아니라 앱 저장소입니다 (`db.studyRuns`, 최근 60개). `study:pull` 이
그걸 위 파일들로 내려받습니다.

런 파일에 **본문을 담지 않습니다.** 남의 글이고, 담으면 저장소가 수십 MB 로 불어납니다.
측정은 받아올 때 끝내고 숫자만 남깁니다.

## 판정을 어떻게 내리나

각 기준마다 경계 후보를 여러 개 놓고, 「경계 이쪽 글」과 「저쪽 글」의 1~3위 비율을 비교합니다.

- **95% 구간(Wilson)이 겹치면 제안하지 않습니다.** 표본 오차를 발견으로 착각하지 않기
  위해서입니다. 이 도구가 만들어진 이유가 정확히 그 실수였습니다.
- 한쪽이 5편 미만인 경계는 건너뜁니다.
- 대상이 20편 미만이면 그 항목은 판정하지 않고 `insufficient` 로 남깁니다.
- 순위는 런별 최고순위의 **중간값**을 씁니다 — 한 번의 우연을 기준으로 삼지 않기 위해서입니다.

판정은 다섯 가지입니다.

| 판정 | 뜻 |
| --- | --- |
| `confirmed` | 데이터가 가리키는 경계가 지금 기준과 같습니다 |
| `keep` | 어느 경계에서도 구간이 갈리지 않았습니다 (표본 오차 안) |
| `stricter` | 확실히 불리해지는 지점보다 **안전한 쪽**에 기준이 있습니다 |
| `change` | 기준이 불리한 쪽에 있습니다 — 고쳐야 합니다 |
| `insufficient` | 표본이 모자랍니다 |

`stricter` 를 따로 둔 이유가 있습니다. 하한 항목에서 이 도구가 찾는 것은 「이 아래로
내려가면 확실히 불리한 지점」입니다. 글자수 절벽이 1,200자에 있다고 해서 목표를 1,200자로
**내리라는 뜻이 아닙니다** — 우리 기준 1,750자는 절벽 위쪽, 안전한 자리입니다.
(첫 판에서 이 갈래가 없어서 「제안: 1750 → 1200」이라고 출력했고, 그건 앱을 나쁜 쪽으로
끌고 가는 조언이었습니다.)

## 기준을 바꿀 때

`analyze` 는 **lib/ 를 자동으로 고치지 않습니다.** 「제안: 4 → 6」처럼 출력하고 끝냅니다.
숫자 하나를 바꾸면 근거 주석과 테스트 단정문도 같이 옮겨야 하고, 그 판단은 사람이 합니다.

제안을 받아들일 때 손대는 곳:

1. `lib/` 의 상수 (리포트가 파일·이름을 같이 알려줍니다)
2. **그 상수 위의 근거 주석** — 어떤 표본에서 어떤 숫자가 나왔는지 적습니다
3. `scripts/checks.mjs` 의 단정문 — 새 숫자로 옮기고, 왜 옮겼는지 주석에 남깁니다
4. 필요하면 `lib/writing/templates.ts` · `lib/ai/prompt.ts` 의 지시문 (AI 에게 시키는 말)

3번과 4번을 빼먹으면 기준이 조용히 어긋납니다 — 검수는 새 숫자로 재고 AI 는 옛 숫자로
쓰는 상태가 됩니다.

## 톤은 「관찰만」 합니다

리포트의 톤 묶음은 **기준 점검 표에 들어가지 않습니다.** 제안도 내지 않습니다.

재봤더니 톤 지표 중 순위와 관계있는 것이 하나도 없었습니다 (방문자 화자를 걸러낸 84편,
전부 |ρ| ≤ 0.21):

```
                      1~3위   7위이하   상관ρ
구어체 (거든요/더라고요)    0.36    0.52    -0.04
1인칭 (제가/저희)         0.70    0.64    +0.03
감정 낱말              0.94    0.57    -0.01
느낌표                3.94    9.11    +0.21
이모지                2.62    3.36    -0.01
회원 말 인용            0.00    0.00    +0.01
```

**그래서 톤은 순위를 잃을 걱정 없이 정할 수 있습니다.** 우리 톤은
`lib/ai/prompt.ts` 의 `TONE` 에 「브랜드 판단」으로 적혀 있고, 순위 근거가 아니라고
명시해 뒀습니다. 순위 데이터가 바뀌어도 이 항목은 흔들리지 않아야 합니다 — 근거의 종류가
다르기 때문입니다.

톤을 매 런 기록하는 이유는 회원 질문이 「**요즘** 상위 블로그가 친근해진 것 같다」였기
때문입니다. 한 번 재서 아니라고 답하는 것과, 계속 재서 변하는지 보는 것은 다릅니다.
어떤 톤 지표든 |ρ| ≥ 0.3 이 되면 리포트가 「관계가 보임」이라고 표시하고 재검토를 권합니다.

**방문자 화자는 제외하고 봅니다.** 후기글은 원래 따뜻해서, 섞어서 세면 「업체 글도 후기처럼
쓰라」는 잘못된 결론이 나옵니다. 우리 홍보·정보글의 비교 대상은 비방문자 글입니다.

## 같은 자로 잰다

조사는 앱이 실제로 쓰는 함수를 그대로 불러옵니다 (`scripts/complib.mjs` 가 `lib/` 를 임시
컴파일합니다):

- `countSignals` — 정보·홍보·경험 종류 세기
- `parsePostMetrics` — 글자수·이미지·영상
- `splitSentences` · `endingOf` — 어미 비중

조사는 A 로 세고 검수는 B 로 세면 "기준을 실측으로 잡았다"는 말이 거짓이 됩니다.
